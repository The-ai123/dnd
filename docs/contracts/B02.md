# B02 storage contract

The desktop engine utility process opens and holds the catalog under the application data directory. The storyteller diagnostics report the catalog schema after startup succeeds. The development scene still comes from the desktop fixture. B03 can use the world asset directory and B04 can build the command transaction on the repository.

| Path | Owner and purpose |
| --- | --- |
| `application-data/catalog.sqlite` | Installation catalog with world instance UUID, canonical folder and display name |
| `world-folder/world.sqlite` | One world's identity, current records and indexed record links |
| `world-folder/manifests/world.json` | Format 1 identity manifest with the same UUID as the database |
| `world-folder/assets/sha256/` | Reserved for immutable originals |
| `world-folder/derived/` | Reserved for rebuildable derivatives |

## Repository lifecycle

1. Open `CatalogRepository` on the application data directory in the authority process.
2. Provision a world with `WorldRepository.open(folder, worldInstanceId, true)`. Keep the same folder and B01 UUID when retrying. SQLite creates the identity in the schema transaction. The manifest is written to a flushed temporary file and renamed into place while the writer owns the database.
3. Pass the resulting repository to `catalog.registerWorld(world, name)`. Registration is a separate catalog transaction. A retry after interrupted provisioning or registration can reopen the same identity and register it again. The catalog enforces uniqueness of both UUID and canonical folder. World registration and schema initialization do not share a transaction.
4. Use `catalog.openWorld(worldInstanceId)` to reopen a registered world. Close repositories when their writer lifetime ends. SQLite releases the file lock on process exit.

Catalog schema 1 and world schema 2 use distinct SQLite application IDs. Ordered migrations, identity checks, the foreign-key check and the new schema version share one transaction. A failed upgrade rolls back. Existing worlds with newer schema versions or mismatched identities fail to open. SQLite uses exclusive writer locking, a bounded busy timeout, WAL and FULL synchronous durability. On Windows, startup checks that the storage path resolves to a fixed local drive. Opening a world validates its manifest and rejects linked database files and linked internal storage directories.

## Records

Record keys use B01's `kind` and UUID. The containing world qualifies each key, so copied or independent worlds can have matching internal record IDs. Each record carries its record version, document format version and JSON payload. `write(record, links)` replaces the current record and its outgoing links in one transaction. The database rejects links whose target does not exist in that world. `get` and `linksFrom` read the current stored data.

B04 owns comparing expected versions, multi-record command transactions, deduplication, revision history and post-commit publication. Later tasks own domain-specific schemas, Trash, recoverable file operations, product backups and restore.

## Verification

The persistence integration tests exercise two isolated sample worlds, matching internal IDs, atomic link validation, writer contention, interrupted provisioning, a version-one upgrade, newer-schema rejection and abrupt process exit inside a migration. The packaged smoke test checks that desktop startup opens the catalog and keeps the catalog diagnostics on the storyteller side of the IPC boundary.
